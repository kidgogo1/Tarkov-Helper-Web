# 프리셋 편집기 외형·회전·슬롯 배치 추가 조사

조사일: 2026-09-07. 상태: 소스 조사와 제한된 각도 확장 구현·검증 기록이며, 외부 공급자와의 계약 또는 전체 부품 지원 인증이 아니다.

## 핵심 결론

현재 구조에서도 **부품을 교체하면 실제 조립 외형 사진이 바뀌고, 각도를 바꾸어 다른 방향의 사진을 보는 프리셋 편집기**를 만들 수 있다. 이미 앱이 사용하는 공급자의 일반 HTTP 렌더링 경로가 이에 해당한다. 그러나 이것은 브라우저에서 모델을 직접 회전하는 3D 렌더러가 아니다.

이번에 확인한 공개 공급자 응답과 작성자 소스에서는 **최신 타르코프의 모든 부품 모델과 정확한 부착점 좌표를 함께 배포하는 독립 웹 SDK를 확보하지 못했다.** 존재하지 않는다는 전세계적 단정은 아니다. 구현 가능한 화면 상호작용과 아직 확보하지 못한 모델 데이터를 구분해야 한다.

권장 범위는 중앙 조립 외형, 선택 부위 강조, 부품 이미지 카드, 부모·하위 부품 연결, 호환 부품 선택, 프리셋 저장 및 구매 목록이다. 임의로 만든 선의 끝점을 실제 게임의 정밀 부착점이라고 설명해서는 안 된다.

## 추가 구현 전 확인한 제품 구조

로컬 `package.json`: React 19.2.8 범위, Vite 8.2.0 범위, TypeScript 5.9.3 범위. 3D 엔진 의존성은 등록되어 있지 않다. 이 수치는 package 선언이며 잠금 파일의 정확한 설치 버전 검증을 대체하지 않는다.

`server/weapon-preview.mjs`와 [기존 결정 문서](../decisions/006-assembled-weapon-preview.md)를 읽었다.

- 로컬 요청은 `POST /api/modding/preview`, 입력은 `{ root: BuildNode, angle: -30 | 0 | 30 }`이다.
- 부모 아이템별 외부 슬롯 정의로 로컬 슬롯 ID를 Unity 슬롯 이름에 대응시킨다. 지원하지 않는 슬롯·부품이면 `SLOT_UNAVAILABLE`이다.
- 결과는 검증된 `data:image/...;base64,...` 이미지다. GLB, 메시, 카메라, 부착점은 반환하지 않는다.
- 동일 구성 캐시, 진행 중 요청 합치기, 단일 작업, 시간·크기 제한, 429 대기 처리를 유지한다.
- 외형 실패 시 미지원 부품을 몰래 제거하거나 기본 총기 사진을 현재 구성의 성공 결과처럼 표시하면 안 된다.

## 1. 기존 이미지 공급자가 실제로 제공하는 것

공급자: [Tarkov Image Generator의 공개 빌드 화면](https://image-gen.tarkov-changes.com/build).

공개 화면이 참조한 [빌드 JavaScript](https://image-gen.tarkov-changes.com/_next/static/chunks/app/build/page-936bbdef166c3d56.js)를 읽었다. 해시가 붙은 파일은 공급자 배포 시 변경될 수 있으므로 안정된 SDK 문서로 취급하지 않는다.

### 실제 응답으로 재확인한 슬롯 정보

[M4A1 슬롯 조회](https://image-gen.tarkov-changes.com/api/item-slots/5447a9cd4bdc2dbd208b4567)에 일반 GET 1회를 보내 HTTP 200을 확인했다.

```text
최상위: slots, toggleProps
슬롯 수: 6
슬롯 필드:
  parentTplId, parentName, slotName, slotId,
  allowedFilterIds, resolvedItemTplIds,
  resolvedItemNames, resolvedItemToggleProps

예시:
  parentTplId: 5447a9cd4bdc2dbd208b4567
  slotId:      55d354084bdc2d8c2f8b4568
  slotName:    mod_pistol_grip
```

이 응답에는 슬롯의 화면 좌표, 월드 좌표, 변환 행렬, 메시 경로가 없다. 관측한 응답에는 `Access-Control-Allow-Origin`도 없었다. 그래서 현재의 고정 공급자 로컬 중계는 유지할 이유가 있다. 관측 범위 밖의 비공개 API 존재 여부는 확인하지 않았다.

### 회전은 현재 앱보다 넓은 입력을 공개 UI에서 사용한다

공급자 UI는 X와 Y 회전 슬라이더 각각 `-180`부터 `180`, 간격 `5`를 사용한다. 정면은 `/api/generate-build`, 회전 값이 있으면 `/api/generate-build-rotated`를 호출한다. 구조는 다음과 같다.

```json
{
  "data": {
    "id": "구성 루트 인스턴스 ID",
    "items": [
      {
        "_id": "구성 루트 인스턴스 ID",
        "_tpl": "총기 아이템 ID",
        "slotId": "FirstPrimaryWeapon"
      },
      {
        "_id": "부품 인스턴스 ID",
        "_tpl": "부품 아이템 ID",
        "parentId": "구성 루트 인스턴스 ID",
        "slotId": "mod_pistol_grip"
      }
    ],
    "rotationX": 0,
    "rotationY": 30
  }
}
```

앱의 세 각도 제한은 우리 API의 초기 계약이었다. 소스 조사 단계에서는 새로운 각도 조합에 생성 POST를 보내지 않았다. 이후 요청받은 각도 확장 구현 및 제한된 실요청 결과는 아래에 별도로 기록한다.

공개 UI에는 접기/펴기와 일부 부품 토글도 있다. `Foldable` 또는 `Retractable` 능력을 확인하고 `upd.Foldable.Folded`를, `HasHinge`를 확인하고 `upd.Togglable.On`을 변경한다. 이것은 추가 구현 후보이지 현재 앱이 이미 지원한다는 뜻이 아니다. 입력 계약·저장·캐시 키·성능 표시까지 함께 설계한 뒤 대상 부품으로 별도 검증해야 한다.

### 권장 회전 UX

- 즉시 반응하는 확대·이동은 받은 이미지에 로컬로 적용한다. 이를 3D 회전이라 부르지 않는다.
- 각도 변경은 드래그 종료 또는 정해진 버튼에서 한 번 요청한다. 손가락/마우스 이동마다 생성하지 않는다.
- 생성 중에는 마지막 성공 외형과 “다른 각도 생성 중” 상태를 유지한다. 오래된 결과로 최신 구성을 덮어쓰지 않는다.
- 같은 구성·각도는 재사용한다. 각도별 대량 사전 생성은 하지 않는다.
- 정밀 연결 좌표가 없는 다른 각도에서는 부품 목록/구조 연결을 사용한다. 정면에서의 임의 앵커를 그대로 붙여 정확한 위치처럼 보이지 않게 한다.

이 UX는 외부 PNG 응답을 사용하는 현재 구조에서의 설계 제안이며, 공급자 처리량 보장이나 무제한 호출 허가를 의미하지 않는다.

실제 적용된 앱은 이전 외형을 현재 조립의 결과로 오해하지 않도록, 구성·적용 각도가 달라지면 기존 생성 이미지를 즉시 숨기는 정책을 유지했다. 위의 마지막 이미지 유지 제안과는 구분한다. 자세한 구현 결정은 [007](../decisions/007-preset-editor-workbench.md)에 기록한다.

## 2. EFTForge의 공간 배치는 실제 3D 부착점이 아니다

작성자 [EFTForge 저장소](https://github.com/SouthHorizons76/EFTForge)의 고정 커밋 `fb83a7f3f53565313e2e01377b5fd5e7b410b42e`를 대상으로 공개 소스를 읽었다. README가 설명하는 화면도 2D 그리드와 재귀 부품 트리, 조립 이미지다.

[attachment-grid.js](https://github.com/SouthHorizons76/EFTForge/blob/fb83a7f3f53565313e2e01377b5fd5e7b410b42e/frontend/modules/attachment-grid.js)에는 다음 구조가 있다.

- 총기·개머리판 기준 열, 위/아래/좌측 슬롯 종류별 배치 규칙.
- `window._AG_OVERRIDES`의 대규모 수동 행/열 보정표.
- `slotId@parentItemId`와 반복 인스턴스 번호를 구분하는 보정 키.
- `computeGridPositions`의 자리 예약, 충돌 회피, 하위 슬롯과 추가 행 배치.

즉 이 자료는 읽기 쉬운 부품 구조도에 참고할 수 있지만, 게임 모델의 월드 좌표나 카메라 투영 데이터는 아니다. 수동 그리드 보정표를 이미지 위의 정확한 부착점으로 변환할 근거도 없다.

[backend/main.py](https://github.com/SouthHorizons76/EFTForge/blob/fb83a7f3f53565313e2e01377b5fd5e7b410b42e/backend/main.py)의 `/build-image`는 같은 이미지 공급자를 이용하며 최종 이미지 URL을 처리한다. 해당 저장소의 브라우저 자동화·응답 가로채기 경로는 복사하거나 실행하지 않았다. 우리 프로젝트는 이미 확인한 일반 HTTP 경로만 사용한다.

이 저장소의 [MIT 라이선스](https://github.com/SouthHorizons76/EFTForge/blob/fb83a7f3f53565313e2e01377b5fd5e7b410b42e/LICENSE)는 소스 재사용을 검토할 근거다. 별도 공급자의 이용 조건이나 게임 모델·텍스처 배포 권한을 대신하지 않는다. 이번 작업에서 제품 코드로 복사한 것은 없다.

## 3. SPT와 공개 SDK의 위치

### TarkinItemExporter: 조립 결과를 내보내는 경로는 실제로 존재

이전에 보관한 TarkinItemExporter 커밋 `f21ac13c7c772b3e37cce53e55bc2832ba89fce1`은 SPT 게임 검사 창의 `WeaponPreviewCamera` 아래 조립 객체를 [내보내기 함수로 전달](https://github.com/bmpq/TarkinItemExporter/blob/f21ac13c7c772b3e37cce53e55bc2832ba89fce1/UI/PatchItemSpecificationsPanel.cs)한다. [Exporter.cs](https://github.com/bmpq/TarkinItemExporter/blob/f21ac13c7c772b3e37cce53e55bc2832ba89fce1/Exporter.cs)는 glTF/GLB를 생성한다. 이번 추가 조사에서는 내보내기를 실행하지 않았다.

이미 조립된 한 가지 구성을 GLB로 확보하면 일반 브라우저 뷰어로 회전할 가능성이 있다. 그러나 프리셋 편집기에서 모든 부품을 실시간 교체하려면 부품별 모델, 슬롯 대응, 부모/자식 변환, 재질·가림·버전 규칙까지 필요하다. 이 플러그인은 바로 연결할 수 있는 HTTP SDK가 아니다.

확인한 프로젝트 설정은 `SPT_4_0`, 버전 1.3.1이다. 최신 라이브의 전 부품 지원으로 확대 해석하면 안 된다. 상세 소스·제약은 별도 보관된 `work/spt-modding-research-2026-09-07/integration-findings.md`에 기록했다.

### EscapeFromTarkov-SDK: Unity 제작 도구이지 웹 실행 SDK가 아님

기존 주소는 현재 작성자의 [EscapeFromTushonka-SDK](https://github.com/S3RAPH-1M/EscapeFromTushonka-SDK) 저장소로 연결된다. README는 Unity Hub와 Unity 2022.3.43 설치, 커스텀 총기·캐릭터·아이템 제작, 에셋 번들 작성 및 뷰어를 설명한다. 이것만으로 공식 타르코프의 최신 전 모델과 좌표를 자유롭게 웹에 배포할 수 있다고 말할 근거는 없다. 설치하거나 번들 뷰어를 실행하지 않았다.

### WeaponCustomizer: 런타임 부품 이동 기능의 참고 자료

작성자의 [WeaponCustomizer](https://github.com/tyfon7/WeaponCustomizer)는 SPT 모딩 화면의 부품 점을 드래그하고 보조 키로 축 이동·회전을 변경하며 프리셋에 보관하는 기능을 설명한다. 게임 안의 장착 객체를 다루는 플러그인이며 웹 모델 저장소가 아니다. 제작자도 충돌·물리적 배치 제한을 강제하지 않는다고 명시한다. 따라서 이 UX를 참고할 수는 있어도 모든 부품의 올바른 좌표 데이터로 사용할 수는 없다.

## 4. 이번 제품 구현에 적용할 판단

| 기능 | 현재 가능한 경로 | 표시해야 할 한계 |
| --- | --- | --- |
| 부품 교체 후 중앙 외형 변경 | 기존 고정 공급자에서 현재 구성 PNG 생성 | 공급자 지원 부품에 한함. 실패를 현재 외형 성공으로 숨기지 않음 |
| 다른 방향 확인 | 검증된 각도 버튼, 이후 제한된 X/Y 요청 확장 | 원격 정지 이미지의 각도 변경이며 실시간 모델 회전이 아님 |
| 중앙 총기를 가리지 않는 부품 카드 | 이미지 바깥 배치, 선택 시 연결 강조, 하위 슬롯 펼치기 | 구조 안내용 연결이며 정밀 부착점 아님 |
| 정확한 부위의 점·선 | 검증된 모델/카메라/부착점 자료 또는 특정 이미지별 검수 좌표가 있을 때 | 일반 슬롯 이름만으로 정확도를 주장하지 않음 |
| 부품 교체와 연속 3D 회전 | 허용된 모델·재질·부착점 묶음 및 조립 렌더러 추가 개발 | 현재 확보된 독립 SDK 없음. 전 부품 지원 보장 불가 |
| 사용자 게임 중 사용 | 로컬 UI와 외부 PNG 서비스 | SPT 실행·게임 파일 접근·내보내기를 백그라운드에서 시작하지 않음 |

이번 판단의 목적은 사용자가 원하는 인게임 편집 흐름을 최대한 구현하되, 확보하지 못한 3D 데이터를 가진 것처럼 꾸미지 않는 것이다. 단계적 구현이 완전한 3D 기능을 구현 완료했다는 의미는 아니다.

## 조사 범위와 검증 기록

- 수행: 기존 로컬 미리보기 코드·결정 문서 읽기, 이미 보관한 SPT 소스 조사 재사용, 작성자 공개 페이지/소스 읽기, 공급자 M4 슬롯 GET 1회.
- 소스 조사 단계에서는 추가 렌더 생성 POST와 제품 코드 수정을 하지 않았다. 이후 별도 요청에 따른 각도 확장 구현은 아래에 기록한다.
- 수행하지 않음: 전 부품 원격 순회, 계정·쿠키 사용, 보호 우회, 게임 설치/실행/접근, 모델·텍스처 추출, 외부 소스 빌드, 커밋·릴리즈.
- 알려진 미지원 Ravage 사례를 자동 부품 제거로 우회하지 않았다.
- 미확인: 아래 두 경우 외의 새 X/Y 조합 실제 생성 결과, 접힘 상태별 결과, 공급자의 서비스 유지·호출량 계약, 최신 전 부품 지원률, 자산별 재배포 권한. 별도 검증 없이 완료로 표시하지 않는다.

## 후속 구현: 15도 간격 각도 확장

별도 구현 요청에 따라 `{ root, angle }` 필드를 유지하면서 Node 서버, 프런트엔드 훅, 포터블 서버의 허용 각도를 **-180~180 범위 정수, 15의 배수**로 확장했다. 기존 -30/0/30 요청은 계속 유효하다. 소수, 범위 밖 값, 문자열·불리언·null 등의 잘못된 자료형은 반올림하거나 잘라서 받지 않고 거부한다. JSON 숫자 `90.0`은 수학적으로 정수 90이며 Node/포터블 모두 같은 숫자와 캐시 키로 처리한다.

기존 고정 공급자, 요청 간격, 단일 생성 작업, 429 대기, 시간 제한, 이미지 검증, 오래된 프런트엔드 요청 무시 규칙은 변경하지 않았다. 외부 API 응답에 없는 정확한 부착점이나 GLB를 추가한 것은 아니다. 접힘·토글·X축 회전도 이번 변경에 포함하지 않았다.

### 테스트 우선 검증

- 변경 전: 추가 각도 서버 테스트 2개와 잘못된 각도 훅 테스트 6개 실패를 확인했다.
- 변경 후: 서버 18개, 훅 16개 테스트 통과. 서버 테스트가 -180부터 180까지 25개 눈금을 전부 확인한다.
- 기존 각도별 캐시·429·동시 작업 제한·타임아웃 및 오래된 요청 보호 테스트도 유지했다.
- 포터블은 -180도 요청이 기존 코드에서 HTTP 400이 되는 실패부터 확인하고 같은 계약으로 변경했다. 최종 포터블 3개 통합 테스트(각도·캐시·응답 보안·429·타임아웃) 모두 통과했다.
- 기존 과대 응답 테스트가 Content-Length와 실제 본문 길이를 다르게 보내 연결 정리 오류까지 섞어 검사하는 점을 바로잡았다. 헤더와 본문이 일치하는 6 MiB 응답으로 크기 제한 거부를 검증한다. 제품의 보안 한도와 오류 처리는 변경하지 않았다.
- 전체 TypeScript 검사 및 변경한 JavaScript/TypeScript 파일 lint를 통과했다.

### 제한된 실제 공급자 요청

카탈로그의 정확한 M4A1 기본 프리셋 `5af08cf886f774223c269184`, 총기 `5447a9cd4bdc2dbd208b4567`, 루트 포함 13개 노드를 사용했다. 카탈로그 버전은 `2026-08-26T04:54:15.220Z`다. 사용자의 실제 게임·로그·프로필에서 구성을 가져오지 않았다.

## 독립 리뷰에서 발견한 작업 초안 보존 결함

히스토리와 저장 연결을 읽기 전용 리뷰하는 과정에서 기존 `weapon-build-storage.ts`가 읽을 수 없는 저장 문자열을 빈 성공 결과로 처리하는 문제를 확인했다. 메모리 저장소에 `schemaVersion: 2`와 총기 A 초안을 둔 뒤 총기 B 저장을 호출하자 `true`를 반환하고 기존 문자열을 `schemaVersion: 1`의 B만 있는 내용으로 교체했다. 이 재현은 실제 사용자 저장소를 사용하거나 수정하지 않았다.

원인은 파서가 손상 JSON·미지원 버전에도 `[]`를 반환하고 읽기 계층이 이를 `ok: true`로 포장한 것이다. 따라서 화면의 자동 저장·실행 취소 저장에서 저장 실패 안내도 나오지 않았다. 신규 히스토리 코드가 만든 회귀가 아니라 이전부터 있던 저장 계층의 보존 문제다.

별도 수정 요청을 받아 다음과 같이 변경했다.

- 저장 키가 없거나 정상 스키마의 빈 배열이면 정상적인 초기 저장을 허용한다.
- 손상 JSON, 미지원 스키마, 기존 빈 문자열, 잘못된 컬렉션/항목, 중복 총기 항목이면 읽기 실패로 구분한다.
- 이 상태의 저장 및 초기화는 `false`를 반환하며 원본 문자열을 수정·삭제하지 않는다.
- 정상 초안 저장·최대 보관 개수·이름 붙인 모딩 라이브러리·업데이트 로직은 변경하지 않았다.

변경 전 보존 테스트 7개가 실패했고 변경 후 저장 서비스 테스트 16개가 통과했다. 라이브러리·히스토리·히스토리 훅을 합한 4개 파일의 43개 테스트도 통과했다. 같은 시점의 Page 전체 회귀에서는 병행 UI 변경에 따른 상태 요소/이미지 대체 텍스트 기대값 불일치 3건을 주 담당자에게 전달했다. 저장 서비스에 대한 수정과 이 UI 검증 결과는 구분한다.

후속 보완으로 이미 저장된 컬렉션이 32개를 초과한 경우도 부분 읽기 후 덮어쓰지 않도록 거부했다. 정상 새 저장의 32개 보관 정책은 유지한다. 저장 서비스 17개 테스트를 통과했고, UI의 중복 상태 요소·닫힌 확대 창의 중복 이미지도 해결한 최종 전체 단위 테스트는 71개 파일/814개 통과다. 최종 화면 검증과 실행 방법은 [007 검증 기록](../decisions/007-preset-editor-workbench.md#최종-검증-및-재현)에 정리했다.
